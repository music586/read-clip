## What are agents?  什么是代理人？

"Agent" can be defined in several ways. Some customers define agents as fully autonomous systems that operate independently over extended periods, using various tools to accomplish complex tasks. Others use the term to describe more prescriptive implementations that follow predefined workflows. At Anthropic, we categorize all these variations as **agentic systems**, but draw an important architectural distinction between **workflows** and **agents**:  

“代理”可以有多种定义方式。一些客户将代理视为完全自主的系统，这些系统能够在长时间内独立运行，并利用各种工具来完成复杂的任务。另一些客户则使用这个术语来描述那些遵循预定义工作流程的特定实现方式。在 Anthropic 公司，我们将所有这些变体都归类为代理系统，但同时强调工作流程与代理之间的重要架构差异。

-   **Workflows** are systems where LLMs and tools are orchestrated through predefined code paths.  
    工作流程是一种系统，其中大型语言模型和工具通过预定义的代码路径来协同运作。
    
-   **Agents**, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.  
    而代理则是一种由大语言模型主导的系统，它们能够自主地指挥自己的进程和工具的使用方式，从而能够掌控完成任务的方式。

Below, we will explore both types of agentic systems in detail. In Appendix 1 (“Agents in Practice”), we describe two domains where customers have found particular value in using these kinds of systems.  
下面，我们将详细探讨这两种代理系统。在附录 1《实践中的代理》中，我们描述了两个领域，客户认为在这些领域中使用这类系统具有显著的价值。

## When (and when not) to use agents  
何时使用代理，何时不使用代理

When building applications with LLMs, we recommend finding the simplest solution possible, and only increasing complexity when needed. This might mean not building agentic systems at all. Agentic systems often trade latency and cost for better task performance, and you should consider when this tradeoff makes sense.  
在构建使用 LLM 的应用程序时，我们建议寻找最简单的解决方案，只有在确实需要时才增加复杂性。这意味着可能完全不构建具有智能代理的系统。虽然智能代理系统通常会以较低的延迟和较低的成本换取更好的任务性能，但您应该考虑是否真的有必要进行这种权衡。

When more complexity is warranted, workflows offer predictability and consistency for well-defined tasks, whereas agents are the better option when flexibility and model-driven decision-making are needed at scale. For many applications, however, optimizing single LLM calls with retrieval and in-context examples is usually enough.  
当需要更高的复杂性时，工作流程能够为定义明确的任务提供可预测性和一致性；而当需要大规模灵活性与基于模型的决策时，代理则是最佳选择。不过，对于许多应用场景来说，仅通过调用 LLM 并结合上下文示例来优化任务通常就足够了。

何时以及如何使用框架。

有许多框架可以使得代理系统更易于实现，其中包括：

    由 AWS 提供的 Strands Agents SDK；

    Vellum，另一种用于构建和测试复杂工作流程的图形化工具。

These frameworks make it easy to get started by simplifying standard low-level tasks like calling LLMs, defining and parsing tools, and chaining calls together. However, they often create extra layers of abstraction that can obscure the underlying prompts ​​and responses, making them harder to debug. They can also make it tempting to add complexity when a simpler setup would suffice.  
这些框架通过简化标准的基础任务，如调用大型语言模型、定义和解析工具以及连接这些任务，使得入门变得非常简单。不过，它们通常会增加额外的抽象层次，这可能会使得底层提示和响应难以被理解，从而增加了调试的难度。此外，当更简单的设置就能满足需求时，使用这些框架可能会让人倾向于添加更多的复杂性。

We suggest that developers start by using LLM APIs directly: many patterns can be implemented in a few lines of code. If you do use a framework, ensure you understand the underlying code. Incorrect assumptions about what's under the hood are a common source of customer error.  
我们建议开发者直接利用大语言模型 API 来实施各种功能：许多功能只需几行代码就能实现。如果你确实需要使用某个框架，请确保你理解其背后的实现原理。对底层逻辑的误解往往是导致客户错误的原因。

## Building blocks, workflows, and agents  
构建模块、工作流程以及代理程序

In this section, we’ll explore the common patterns for agentic systems we’ve seen in production. We'll start with our foundational building block—the augmented LLM—and progressively increase complexity, from simple compositional workflows to autonomous agents.  
在这一部分中，我们将探讨在工业生产中常见的智能系统模式。我们首先从基础构建模块——增强型大语言模型开始，然后逐步增加复杂性，从简单的组合式工作流程到自主智能体。

### Building block: The augmented LLM  
构建模块：增强版的 LLM

The basic building block of agentic systems is an LLM enhanced with augmentations such as retrieval, tools, and memory. Our current models can actively use these capabilities—generating their own search queries, selecting appropriate tools, and determining what information to retain.  
代理系统的基本组成部分是一个经过增强的大型语言模型，该模型配备了诸如检索、工具和记忆等功能。我们的当前模型能够主动使用这些功能——生成自己的搜索查询、选择合适的工具，并决定保留哪些信息。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2Fd3083d3f40bb2b6f477901cc9a240738d3dd1371-2401x1000.png&w=3840&q=75)

The augmented LLM  增强版的大语言模型

We recommend focusing on two key aspects of the implementation: tailoring these capabilities to your specific use case and ensuring they provide an easy, well-documented interface for your LLM. While there are many ways to implement these augmentations, one approach is through our recently released [Model Context Protocol](https://www.anthropic.com/news/model-context-protocol), which allows developers to integrate with a growing ecosystem of third-party tools with a simple [client implementation](https://modelcontextprotocol.io/tutorials/building-a-client#building-mcp-clients).  
我们建议重点关注实施的两个关键方面：一是将这些功能适配到你的具体应用场景中；二是确保它们能为你的大语言模型提供一个简单且文档齐全的接口。虽然实现这些增强功能有多种方法，但其中一种方式就是通过我们最近发布的“模型上下文协议”。通过这一协议，开发者可以轻松地将其与越来越多的第三方工具集成在一起，而无需复杂的客户端实现。

For the remainder of this post, we'll assume each LLM call has access to these augmented capabilities.  
在接下来的文章中，我们假设每个 LLM 都能访问这些增强的功能。

### Workflow: Prompt chaining  
工作流程：提示链式操作

Prompt chaining decomposes a task into a sequence of steps, where each LLM call processes the output of the previous one. You can add programmatic checks (see "gate” in the diagram below) on any intermediate steps to ensure that the process is still on track.  
快速链接将任务分解为一系列步骤，每个大型语言模型都会处理前一步骤的输出结果。你可以在任何中间步骤中添加程序化的检查机制（参见下图中的“门”符号），以确保整个过程能够顺利进行。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F7418719e3dab222dccb379b8879e1dc08ad34c78-2401x1000.png&w=3840&q=75)

The prompt chaining workflow  
提示链式工作流程

**When to use this workflow:** This workflow is ideal for situations where the task can be easily and cleanly decomposed into fixed subtasks. The main goal is to trade off latency for higher accuracy, by making each LLM call an easier task.  
何时使用此工作流程：当任务可以轻松且清晰地分解为多个固定子任务时，此工作流程尤为适用。其主要目的是通过让每次调用大型语言模型变得更加简单，从而在提高准确性的同时降低延迟。

**Examples where prompt chaining is useful:  
需要快速链接使用的场景示例：**

-   Generating Marketing copy, then translating it into a different language.  
    编写营销文案，然后将其翻译成不同的语言。
-   Writing an outline of a document, checking that the outline meets certain criteria, then writing the document based on the outline.  
    编写文档的提纲，确保提纲符合某些标准，然后根据提纲来撰写文档。

### Workflow: Routing  工作流程：路由处理

Routing classifies an input and directs it to a specialized followup task. This workflow allows for separation of concerns, and building more specialized prompts. Without this workflow, optimizing for one kind of input can hurt performance on other inputs.  
路由功能会对输入数据进行分类，并将其引导至相应的专业处理任务。这种工作流程有助于将不同任务分离开来，从而能够生成更精细化的提示。如果没有这种工作流程，那么针对某种输入数据的优化可能会影响到其他输入数据的性能。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F5c0c0e9fe4def0b584c04d37849941da55e5e71c-2401x1000.png&w=3840&q=75)

The routing workflow  路由工作流程

**When to use this workflow:** Routing works well for complex tasks where there are distinct categories that are better handled separately, and where classification can be handled accurately, either by an LLM or a more traditional classification model/algorithm.  
何时使用此工作流程：当任务较为复杂，需要区分不同的类别并分别处理时，或者当分类工作需要由大语言模型或更传统的分类模型/算法来准确完成时，使用路由流程是非常合适的。

**Examples where routing is useful:  
路由派发具有实用性的场景示例：**

-   Directing different types of customer service queries (general questions, refund requests, technical support) into different downstream processes, prompts, and tools.  
    将各种客户服务请求（如常见问题、退款请求、技术支持等）分配到不同的下游流程、提示信息以及相应的工具中处理。
-   Routing easy/common questions to smaller, cost-efficient models like Claude Haiku 4.5 and hard/unusual questions to more capable models like Claude Sonnet 4.5 to optimize for best performance.  
    将简单/常见的任务分配给性能较低的模型，比如 Claude Haiku 4.5；而将复杂且不寻常的任务分配给能力更强的模型，比如 Claude Sonnet 4.5，以优化性能表现。

### Workflow: Parallelization  
工作流程：并行处理

LLMs can sometimes work simultaneously on a task and have their outputs aggregated programmatically. This workflow, parallelization, manifests in two key variations:  
大型语言模型有时可以同时处理多个任务，其输出结果也可以通过程序的方式进行整合。这种工作流程的并行性表现为两种主要形式：

-   **Sectioning**: Breaking a task into independent subtasks run in parallel.  
    分割：将任务分解为多个独立的子任务，然后并行处理这些子任务。
-   **Voting:** Running the same task multiple times to get diverse outputs.  
    投票：多次执行同一任务，以获得不同的结果。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F406bb032ca007fd1624f261af717d70e6ca86286-2401x1000.png&w=3840&q=75)

The parallelization workflow  
并行化工作流程

**When to use this workflow:** Parallelization is effective when the divided subtasks can be parallelized for speed, or when multiple perspectives or attempts are needed for higher confidence results. For complex tasks with multiple considerations, LLMs generally perform better when each consideration is handled by a separate LLM call, allowing focused attention on each specific aspect.  
何时使用此工作流程：当分割的子任务可以并行处理以提高效率时，或者当需要多个视角或尝试以获得更可靠的结果时，并行化就非常有效。对于包含多个考虑因素的复杂任务，如果每个因素都能由单独的 LLM 来处理，那么 LLM 通常会表现得更好，因为这样就可以专注于每个具体的方面。

**Examples where parallelization is useful:  
并行化有用的场景示例：**

-   **Sectioning**:  分段：
    -   Implementing guardrails where one model instance processes user queries while another screens them for inappropriate content or requests. This tends to perform better than having the same LLM call handle both guardrails and the core response.  
        在多个模型实例处理用户查询时，应实施相应的防护措施，让另一个模型负责检查这些查询是否包含不当内容或请求。这种方式通常比让同一个大语言模型同时处理防护机制和核心响应更为高效。
    -   Automating evals for evaluating LLM performance, where each LLM call evaluates a different aspect of the model’s performance on a given prompt.  
        自动化评估 LLM 性能的过程，其中每次调用 LLM 时，都会针对给定输入提示来评估模型性能的不同方面。
-   **Voting**:  投票：
    -   Reviewing a piece of code for vulnerabilities, where several different prompts review and flag the code if they find a problem.  
        在审查一段代码时，会使用多种不同的工具来检测其中的漏洞。如果发现任何问题，这些工具会分别提示并标记出这些问题。
    -   Evaluating whether a given piece of content is inappropriate, with multiple prompts evaluating different aspects or requiring different vote thresholds to balance false positives and negatives.  
        在评估某篇内容是否不合适时，通常会使用多个提示来考量不同的方面，或者设定不同的投票阈值，以平衡误报和正确判断之间的平衡。

### Workflow: Orchestrator-workers  
工作流程：协调员-工作人员

In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results.  
在协调器-工作者工作流程中，一个中央的大语言模型会动态地将任务分解，将它们分配给各个工作者的大语言模型，然后整合这些模型的成果。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F8985fc683fae4780fb34eab1365ab78c7e51bc8e-2401x1000.png&w=3840&q=75)

The orchestrator-workers workflow  
协调者-员工工作流程

**When to use this workflow:** This workflow is well-suited for complex tasks where you can’t predict the subtasks needed (in coding, for example, the number of files that need to be changed and the nature of the change in each file likely depend on the task). Whereas it’s topographically similar, the key difference from parallelization is its flexibility—subtasks aren't pre-defined, but determined by the orchestrator based on the specific input.  
何时使用此工作流程：此工作流程适用于那些难以预测需要完成哪些子任务的情况。例如，在编程领域，需要修改的文件数量以及每个文件的具体修改内容，都可能取决于具体的任务要求。虽然这种工作流程在结构上与并行处理类似，但其核心区别在于灵活性——子任务并不是预先定义好的，而是根据具体的输入情况由协调器来决定。

**Example where orchestrator-workers is useful:  
在以下例子中，协调器-工作者机制发挥了作用：**

-   Coding products that make complex changes to multiple files each time.  
    编写那些每次都会对多个文件进行复杂修改的编程产品。
-   Search tasks that involve gathering and analyzing information from multiple sources for possible relevant information.  
    那些需要收集来自多个来源的信息，并对这些信息进行分析的任务。目的是找出可能相关的信息。

### Workflow: Evaluator-optimizer  
工作流程：评估者-优化者

In the evaluator-optimizer workflow, one LLM call generates a response while another provides evaluation and feedback in a loop.  
在评估者-优化者工作流程中，一个大语言模型负责生成响应，而另一个则负责进行评估和提供反馈，这两个过程会循环进行。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F14f51e6406ccb29e695da48b17017e899a6119c7-2401x1000.png&w=3840&q=75)

The evaluator-optimizer workflow  
评估者-优化者工作流程

**When to use this workflow:** This workflow is particularly effective when we have clear evaluation criteria, and when iterative refinement provides measurable value. The two signs of good fit are, first, that LLM responses can be demonstrably improved when a human articulates their feedback; and second, that the LLM can provide such feedback. This is analogous to the iterative writing process a human writer might go through when producing a polished document.  
何时使用此工作流程：当我们有明确的评估标准，且迭代优化能够产生可测量的价值时，这种工作流程尤为有效。判断流程是否合适的两个标志是：首先，当人类提供反馈时，大型语言模型的响应能够显著改善；其次，大型语言模型能够给出有效的反馈。这类似于人类作家在创作完善的作品时所经历的迭代写作过程。

**Examples where evaluator-optimizer is useful:  
使用评估器-优化器的场景示例：**

-   Literary translation where there are nuances that the translator LLM might not capture initially, but where an evaluator LLM can provide useful critiques.  
    在文学翻译中，有些细微之处可能由翻译机器人无法捕捉到，而评估机器人则可以给出有价值的反馈意见。
-   Complex search tasks that require multiple rounds of searching and analysis to gather comprehensive information, where the evaluator decides whether further searches are warranted.  
    这类复杂的搜索任务需要多轮搜索和分析才能收集到全面的信息，此时评估者需要决定是否还需要进行进一步的搜索。

### Agents  代理人员

Agents are emerging in production as LLMs mature in key capabilities—understanding complex inputs, engaging in reasoning and planning, using tools reliably, and recovering from errors. Agents begin their work with either a command from, or interactive discussion with, the human user. Once the task is clear, agents plan and operate independently, potentially returning to the human for further information or judgement. During execution, it's crucial for the agents to gain “ground truth” from the environment at each step (such as tool call results or code execution) to assess its progress. Agents can then pause for human feedback at checkpoints or when encountering blockers. The task often terminates upon completion, but it’s also common to include stopping conditions (such as a maximum number of iterations) to maintain control.  
随着大语言模型在关键能力上的不断成熟，智能体开始逐渐应用于实际生产环境中。这些智能体能够理解复杂的输入信息，进行推理和规划，可靠地使用各种工具，并且能够从错误中恢复。智能体的工作通常始于人类用户的指令或互动式对话。一旦任务明确后，智能体就可以独立地执行任务，必要时会向人类用户寻求进一步的指导或判断。在任务执行过程中，智能体需要从环境中获取“真实信息”来评估自己的进展，比如工具调用的结果或代码执行的状况。在关键节点或遇到障碍时，智能体可以暂停以获取人类的反馈。任务通常在完成之后终止，但也会设置一些停止条件（如最大迭代次数），以控制系统的运行。

Agents can handle sophisticated tasks, but their implementation is often straightforward. They are typically just LLMs using tools based on environmental feedback in a loop. It is therefore crucial to design toolsets and their documentation clearly and thoughtfully. We expand on best practices for tool development in Appendix 2 ("Prompt Engineering your Tools").  
这些代理能够处理复杂的任务，但它们的实施通常较为简单。它们通常只是使用基于环境反馈的循环机制来运行的大型语言模型而已。因此，明确且周全地设计工具集及其文档是非常重要的。我们在附录 2《如何编写高效的工具提示》中详细介绍了工具开发的最佳实践。

![](https://www.anthropic.com/_next/image?url=https%3A%2F%2Fwww-cdn.anthropic.com%2Fimages%2F4zrzovbb%2Fwebsite%2F58d9f10c985c4eb5d53798dea315f7bb5ab6249e-2401x1000.png&w=3840&q=75)

Autonomous agent  自主代理程序

**When to use agents:** Agents can be used for open-ended problems where it’s difficult or impossible to predict the required number of steps, and where you can’t hardcode a fixed path. The LLM will potentially operate for many turns, and you must have some level of trust in its decision-making. Agents' autonomy makes them ideal for scaling tasks in trusted environments.  
何时使用智能体：智能体适用于那些难以预测所需步骤数量，或者无法硬编码固定路径的开放性问题。大语言模型可以持续处理多个回合的运算，因此我们需要对其决策结果有一定的信任度。智能体的自主性使得它们非常适合在可信环境中进行大规模任务处理。

The autonomous nature of agents means higher costs, and the potential for compounding errors. We recommend extensive testing in sandboxed environments, along with the appropriate guardrails.  
代理程序的自主性意味着更高的成本，同时也容易出现累积性错误。我们建议在沙盒环境中进行广泛的测试，并采取适当的防护措施。

## Combining and customizing these patterns  
将这些模式进行组合并进行个性化定制

These building blocks aren't prescriptive. They're common patterns that developers can shape and combine to fit different use cases. The key to success, as with any LLM features, is measuring performance and iterating on implementations. To repeat: you should consider adding complexity *only* when it demonstrably improves outcomes.  
这些基础组件并不具有强制性要求。它们只是常见的模式，开发者可以对其进行改造和组合，以适应不同的应用场景。就像任何大型语言模型的功能一样，成功的关键在于衡量性能并不断对实现方式进行优化。需要强调的是：只有当增加复杂性能够明显提升效果时，才应考虑引入更复杂的组件。

## Summary  摘要

Success in the LLM space isn't about building the most sophisticated system. It's about building the *right* system for your needs. Start with simple prompts, optimize them with comprehensive evaluation, and add multi-step agentic systems only when simpler solutions fall short.  
在大型语言模型领域取得成功，并非意味着要构建最复杂的系统。重要的是要打造符合自身需求的合适系统。从简单的提示开始，通过全面的评估来优化这些提示，只有当简单的解决方案无法满足需求时，才考虑使用多步骤的智能系统。

When implementing agents, we try to follow three core principles:  
在部署代理时，我们尽量遵循三个核心原则：

1.  Maintain **simplicity** in your agent's design.  
    在代理设计中保持简洁性。
2.  Prioritize **transparency** by explicitly showing the agent’s planning steps.  
    通过明确展示代理的规划步骤，来优先考虑透明度问题。
3.  Carefully craft your agent-computer interface (ACI) through thorough tool **documentation and testing**.  
    通过详细的工具文档和测试，精心设计你的代理计算机接口（ACI）。

Frameworks can help you get started quickly, but don't hesitate to reduce abstraction layers and build with basic components as you move to production. By following these principles, you can create agents that are not only powerful but also reliable, maintainable, and trusted by their users.  
框架可以帮助你快速入门，但当你进入生产环境时，不妨减少抽象层次，直接使用基础组件进行开发。遵循这些原则，你可以创建出不仅功能强大，而且可靠、易于维护且受到用户信赖的代理程序。

## Appendix 2: Prompt engineering your tools  
附录 2：利用提示工程来操控你的工具

No matter which agentic system you're building, tools will likely be an important part of your agent. [Tools](https://www.anthropic.com/news/tool-use-ga) enable Claude to interact with external services and APIs by specifying their exact structure and definition in our API. When Claude responds, it will include a [tool use block](https://docs.anthropic.com/en/docs/build-with-claude/tool-use#example-api-response-with-a-tool-use-content-block) in the API response if it plans to invoke a tool. Tool definitions and specifications should be given just as much prompt engineering attention as your overall prompts. In this brief appendix, we describe how to prompt engineer your tools.  
无论你正在构建哪种智能体系统，工具都可能是智能体的重要组成部分。通过在我们的 API 中明确指定工具的结构和定义，Claude 就能与外部服务和 API 进行交互。当 Claude 做出响应时，如果它打算调用某个工具，那么其响应中会包含该工具的调用信息。工具的定义和规格说明应该像整体提示设计一样受到精心设计的关注。在这个简短的附录中，我们将描述如何对工具进行提示设计。

There are often several ways to specify the same action. For instance, you can specify a file edit by writing a diff, or by rewriting the entire file. For structured output, you can return code inside markdown or inside JSON. In software engineering, differences like these are cosmetic and can be converted losslessly from one to the other. However, some formats are much more difficult for an LLM to write than others. Writing a diff requires knowing how many lines are changing in the chunk header before the new code is written. Writing code inside JSON (compared to markdown) requires extra escaping of newlines and quotes.  
通常存在多种方式来指定相同的操作。例如，可以通过编写差异报告来指定文件编辑操作，或者重新编写整个文件。对于结构化输出，可以在 Markdown 或 JSON 中返回代码。在软件工程中，这类差异属于微不足道的，可以无损地从一个格式转换为另一个格式。不过，有些格式对于 LLM 来说要编写起来要困难一些。例如，编写差异报告需要知道在编写新代码之前，原始代码块中有多少行发生了变化。而在 JSON 中编写代码（与在 Markdown 中相比）则需要额外处理换行符和引号等问题。

Our suggestions for deciding on tool formats are the following:  
关于工具格式选择的建议如下：

-   Give the model enough tokens to "think" before it writes itself into a corner.  
    给这个模型足够的“线索”，让它能够在将其写入代码之前进行“思考”。
-   Keep the format close to what the model has seen naturally occurring in text on the internet.  
    保持格式与模型所看到的、在互联网上常见的文本格式相似。
-   Make sure there's no formatting "overhead" such as having to keep an accurate count of thousands of lines of code, or string-escaping any code it writes.  
    请确保没有因处理成千上万行代码或处理所编写代码的异常处理而出现的格式问题。

One rule of thumb is to think about how much effort goes into human-computer interfaces (HCI), and plan to invest just as much effort in creating good *agent*\-computer interfaces (ACI). Here are some thoughts on how to do so:  
一个实用的经验法是思考一下在开发人类与计算机交互界面时所需要付出的努力，然后同样投入精力来打造优秀的计算机与代理交互界面。以下是一些关于如何做到这一点的建议：

-   Put yourself in the model's shoes. Is it obvious how to use this tool, based on the description and parameters, or would you need to think carefully about it? If so, then it’s probably also true for the model. A good tool definition often includes example usage, edge cases, input format requirements, and clear boundaries from other tools.  
    请试着站在模型的角度来思考。根据描述和功能参数，是否很容易理解如何使用这个工具？还是说需要仔细考虑一些细节？如果是后者，那么对于模型来说也是如此。一个良好的工具定义通常应包括使用示例、边缘情况、输入格式要求，以及与其他工具的明确区分。
-   How can you change parameter names or descriptions to make things more obvious? Think of this as writing a great docstring for a junior developer on your team. This is especially important when using many similar tools.  
    如何改变参数的名称或描述，以使它们更加易于理解？可以把这看作是为团队中的初级开发人员编写一份优秀的文档说明。当使用许多类似的工具时，这一点尤为重要。
-   Test how the model uses your tools: Run many example inputs in our [workbench](https://console.anthropic.com/workbench) to see what mistakes the model makes, and iterate.  
    测试模型如何使用你的工具：在我们的工作台中运行多个示例输入，观察模型可能出现的错误，并据此进行优化。
-   [Poka-yoke](https://en.wikipedia.org/wiki/Poka-yoke) your tools. Change the arguments so that it is harder to make mistakes.  
    让你的工具具备防错功能。改变算法的参数设置，使得出错变得更加困难。

While building our agent for [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet), we actually spent more time optimizing our tools than the overall prompt. For example, we found that the model would make mistakes with tools using relative filepaths after the agent had moved out of the root directory. To fix this, we changed the tool to always require absolute filepaths—and we found that the model used this method flawlessly.  
在构建用于 SWE-bench 的代理程序时，我们实际上花费了更多的时间来优化工具的使用方式，而不是专注于整体提示语的优化。例如，我们发现，当代理程序已经移出根目录之后，模型在使用相对文件路径时仍然会出错。为了解决这个问题，我们修改了工具的使用方式，要求始终使用绝对文件路径。结果发现，模型在采用这种方法后能够毫无差错地完成任务。
